TMT Radar Architecture

What runs where, what it depends on, and what stands between a working prototype and infrastructure a practice can rely on.

The shape of it

Three lanes, and only one of them does the detecting

The system exists to answer one question on a schedule: has anything been published that changes a client's obligations? Everything else is plumbing around that question.

Detection is deliberately the dumbest part. A registry file describes 57 government listing pages across 17 hosts, and a deterministic Python engine visits them every two hours, compares what it sees against a ledger of what it has already seen, and reports the difference. No language model participates in that decision. A model cannot be talked into inventing a notification, and it cannot quietly decide that a page returning zero rows simply had no news.

Two further lanes sit around it. A scheduled cloud session acts as watchdog and covers the two jobs the local engine structurally cannot do: working the e-Gazette's search flow, and sweeping the trade press for instruments that were never published anywhere. Then a human lane, where an associate turns a detected instrument into a client memo. The model appears only in those outer lanes, and only as transport and drafting, never as the thing that decides whether an instrument exists.

Inside one sweep

Every row ends somewhere you can name

The claim worth defending is not that the scrapers work. It is that when they stop working, you find out. A scraper that silently returns nothing looks exactly like a quiet week at the regulator, and that is the failure mode that actually costs a client a deadline.

So the pipeline has no exit labelled "nothing happened". Every row that enters ends in a named state, and every state that is not ledgered or already known shows up in the health file and on the dashboard.

What it takes to run

Measured, not estimated

The resource profile is the good news. A full pass over all 57 sources takes four and a half minutes of wall time but under ten seconds of processor time, because nearly all of it is deliberate waiting: the engine paces itself to about one request per second per host, so it never behaves like a load test against a government server.

The dependency that actually matters

Not processing, not storage: an unobstructed network path to Indian government hosts. That is exactly what a cloud sandbox could not provide, which is why detection was moved onto a local machine in the first place. Any host you migrate to must be tested against the live sources before it is trusted, never assumed to work merely because it has internet.

The weak point

It runs on one laptop, and it is not yet scheduled

Two gaps to close before anyone relies on this

The schedule is written but not installed. The launch agent file exists and is correct, but it has not been loaded, so nothing sweeps right now unless a person runs it by hand. One command fixes it, and it is the first thing to do.

The host is a personal laptop. When the lid closes, detection stops. When the laptop leaves the firm, the tracker leaves with it. For a tool whose entire value is that it does not miss things, a host that sleeps is a design flaw rather than a detail.

The fix is cheap, precisely because the workload is so small. Three options, in the order I would try them.

A dedicated always-on machine at the firmstart here

A Mac mini or any retired desktop, left switched on. It preserves the exact network path already proven to reach all 57 sources, needs no code changes at all, and can be set up in an afternoon. The tracker stops being one person's laptop and becomes a firm asset.

A small Linux virtual machinetest reachability first

The cheapest tier from any provider is ample for ten seconds of processing every two hours. But do not commit until you have run a real sweep from that host: whether the earlier cloud blockage was an egress policy or Indian sites refusing foreign traffic is still unestablished, and the answer decides whether the machine has to sit in an India region.

A firm-managed server under ITthe eventual answer

The right long-term home for something the practice depends on, with backups and monitoring that outlive whoever built it. Worth doing once the tracker has proved itself over a few weeks, so IT is handed a known quantity rather than an experiment.

Whichever host it lands on, one requirement is not technical: somebody has to own it. Alerts need a person who reads them, and a regulator redesigning their site needs someone to re-capture a page. A tracker nobody watches is worse than no tracker, because it manufactures confidence while quietly going blind.

The limit no architecture removes

Between a third and a half of the instruments that actually bind a TMT client are never published on any website: blocking orders, portal notices to intermediaries, licence amendment letters, advisories served on named parties. No crawler reaches a document that sits on no server.

The press and NGO sweep is a partial net. The complete one is available only to a law firm: when a client forwards a government letter, that letter is the instrument. A disciplined intake log for those would be the single largest coverage gain available, and no amount of engineering substitutes for it.

Operating it

The commands worth knowing

launchctl load ~/Library/LaunchAgents/com.trilegal.tmtradar.plistInstall the two-hourly schedule. Do this first, copying the plist out of engine/ beforehand.
tracker.py selftestParse every source against its saved page capture. Must pass before you trust a change. Currently 57 of 57.
tracker.py sweepRun every source now. Exits non-zero if anything failed.
tracker.py sweep --source IDRe-run one source while fixing its adapter.
tracker.py auditAssert that every stored row still agrees with the classification rules. Catches drift.
tracker.py backfill --since DATEWalk a source's pagination back in time. Used when adding a venue.
tracker.py fetch-pdfsArchive instrument PDFs locally, so a memo cites a file that outlives the government link.
tracker.py healthPer-source status from the last run.

Adding a source, which is the routine maintenance task

Describe the venue in the registry, save one live capture of its page as a fixture, and run the selftest until the adapter parses that capture above a floor you set from the real row count. Then backfill, and commit the registry entry and the fixture together, so the repository always holds the evidence that the adapter once worked against real bytes. Thirteen venues found by the last audit are already registered this way, with verified URLs, waiting for adapters.
